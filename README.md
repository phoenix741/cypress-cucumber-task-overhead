# cypress-cucumber-task-overhead

Minimal, self-contained example measuring the `cy.task` round trips that
[`@badeball/cypress-cucumber-preprocessor`](https://github.com/badeball/cypress-cucumber-preprocessor)
emits in `cypress run` as soon as a report (`json`, `messages`, `html`, ...) is enabled.

To build a report, the preprocessor rebuilds the lifecycle of every scenario in the plugin process. It sends one
`cy.task` when each step, scenario and hook starts and finishes. Every call is a browser -> Cypress server -> plugin
process round trip. Without any report enabled, none of these tasks is sent.

## What is measured

The same two features run against a local static page (`app/index.html`, no network involved) in three variants.
The command log is identical in all variants; only the report changes.

| Variant | Command |
| --- | --- |
| no report | `npm run test:no-report` (`--expose jsonEnabled=false`) |
| JSON report | `npm run test:report` |
| JSON report + batched tasks | `npm run test:report-batched` (`--expose batchTasks=true`) |

Features (generated by `npm run generate`, 40 scenarios each):

- `counter.feature`: 25 steps per scenario, real clicks and assertions in the browser.
- `trivial.feature`: 50 steps per scenario that do nothing in the browser, so the fixed cost per step is not diluted.

Median of 3 rounds, Electron, Cypress 16.2.1, preprocessor 28.0.1, Node 26.10 (`npm run benchmark`):

| Feature | no report | JSON report | JSON report + batched tasks | `cy.task` round trips (report / batched) |
| --- | --- | --- | --- | --- |
| `counter.feature` (1000 steps) | 41 s | 57 s (+39 %) | 47 s (+15 %) | 2081 / 40 |
| `trivial.feature` (2000 steps) | 8 s | 43 s (+438 %) | 16 s (+100 %) | 4081 / 40 |

That is about 8 ms per round trip, whatever the step does. The time spent inside the plugin handlers is negligible:
the cost is the number of round trips, so the overhead is proportional to the number of steps.

## Batching workaround (proof of concept)

`cypress/support/cucumber-task-batching.ts` overwrites `cy.task` so the preprocessor messages are queued in the browser
and sent as one call at the end of each scenario. `cypress/plugins/cucumber-task-batching.ts` replays them in order
on the plugin side. The JSON report is identical to the one produced without batching (durations ignored); the benchmark
checks it.

The remaining overhead comes from the `cy.task` commands themselves, which are still enqueued by the preprocessor even
when they do nothing. Removing it would need a change in the preprocessor.

Limitations: it relies on the preprocessor's internal task names, messages of a scenario that never reaches its end
(browser crash) are lost, and failure screenshots are re-attached at replay time.

## Not covered

This example does not reproduce latencies growing during very long runs, seen on a large real-world suite
(same scenarios 3 to 4 times slower late in a run of about 12000 round trips). A run of 6250 steps and 13000 round
trips, with Chrome, a heavy animated page, proxied requests and uncompressed 1080p video, showed no such drift.
